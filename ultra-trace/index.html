The problem

Swift teams need static analysis that can gate a build offline and still help a human explore risky paths. Chat-only tools blur those jobs and send code to a model.

I needed those contracts kept separate (assist for exploration, gate for CI), and I did not want the model anywhere near the exit code.

Why I built it

Day to day, I use explore when I want to understand paths with optional LLM help, and I use analyze when I need to gate the build.

They share the same engine with different contracts. That is the whole point: one analyzer I can trust in CI, and still lean on day-to-day when I want another careful look at a risky path. I was counting on CI meaning an offline, deterministic exit that optional assist never owns.

What I built

ultra-trace is a deterministic static analysis CLI for Swift (Core), with optional Advanced SIL, bounded call summaries, and a Python frontend. Entry points are ultra-trace and python -m ultra_trace. macOS and Xcode are required to build the SwiftSyntax helper.

Dual mode covers two contracts:

  • explore is day-to-day assist. The LLM is optional. Results stay advisory. The process uses a soft exit unless you pass --fail-on-findings.
  • analyze is the CI / nightly gate. It runs offline with the LLM off. It uses the same analysis engine.

Reports write markdown, JSON, and SARIF, and high findings can carry proof artifacts with tiers. Privacy modes are offline, redacted, and full-assist, while API keys live only in the appdir .env, never in YAML. Phases 1 through 6 are complete, and Phase 7 covers platform maturity: Mac fleet bootstrap, perf budgets, SARIF export, and operator hygiene.

You launch with ultra-trace or python -m ultra_trace.

Three decisions

These are the craft bets I would defend in a design review, each one about honesty, ownership, or maintainability.

1. Dual mode is the product.

Assist and gate share one engine and keep different contracts: explore is human-first and advisory, while analyze owns CI exit codes and severity thresholds. That split is the design, not a flag added later. I split the modes so optional assist never gets to own whether the build fails, which gives me one analyzer I can trust in CI, and still use day-to-day with help when I want it. I was counting on a gate guaranteeing an offline exit code driven by severity thresholds the model cannot rewrite, and on one engine with two contracts being better than two products that drift apart. Dual mode is the product rather than a later flag. Separate contracts on one engine keep a chat tool from drifting into the gate, and keep a gate from shipping half-baked LLM opinions into the exit code.

2. The analyzer owns findings; the LLM stays advisory.

When assist is on, the model may propose an exploration plan, draft advisory wording, or emit optional llm.proposed_candidate items, but it never changes severity, confidence, or proof tier. Offline wins over --llm-enabled. Proposed candidates never fail Core severity gates alone. Severity and proof have to come from the deterministic engine, or CI stops meaning anything. I was counting on severity, confidence, and proof tier only meaning something in CI if they come from the deterministic engine, and on offline winning over a flag as how I prevent turning the gate into an online call by habit. The model can help me look but cannot rewrite the grade. That is not distrust of the model; it is respect for what a gate has to mean.

3. Proofs and privacy are engineered into the product.

High findings get proof tiers: runnable scaffold, repro steps, path witness, or unsupported. Keys stay in the appdir .env, offline blocks network and forces the LLM off, and redacted and full-assist sanitize outbound text. Toolchain pins, drift checks, and SARIF support a Mac fleet and Code Scanning, not a demo script. If a finding can fail a build, I want a path I can inspect offline, not a hunch, and proof tiers make "why did this fail?" answerable. I was counting on a build-failing finding needing a path that is inspectable offline; on privacy modes existing so assist never sends more code than the chosen mode allows; and on fleet operators needing pins and SARIF rather than a demo script. Proofs, privacy, and operator hygiene are engineered into the product instead of left as docs afterthoughts. Privacy modes and appdir keys keep assist optional without turning YAML into a secret store or sending more code than the mode allows. Pins and SARIF are for operators who have to run this on a fleet, not for a one-off demo. The offline path is the point, because trust in a gate starts there.

Why I built it this way

These boundaries are the same ones I hold in iOS work: clear ownership, real persistence of contract, and something a technical peer can judge quickly.

I use dual mode so assist never owns CI. I keep analyzer-owned findings so the model stays advisory. I engineer proofs and privacy so a failing gate has an offline path you can trust. Assist and CI gate stay separate contracts on one deterministic core. The optional LLM can advise; it cannot rewrite the gate. If a finding can fail a build, the path that produced it should be something you can trust offline.
