Bugmiester

A localhost trainer for Swift bug-spotting.

Python · FastAPI · free-text scoring · Code on GitHub

View on GitHub See the proof

The problem

Interview and practice tools usually go one of two ways: multiple-choice quizzes, or a live LLM chat. Neither trains the skill I actually need.

I needed to read a short Swift snippet, name the one real bug in free text, and get a fair score without shipping API keys to a browser or a hosted service.

Why I built it

Day to day, I write Swift with AI now, and that is useful, but it can dull the habit of spotting bugs by eye.

Bugmiester is how I keep that skill sharp: a local trainer where I still have to read the code and name the bug. The model writes the snippets and helps score. It does not do the reading for me.

What I built

Bugmiester is a FastAPI app on 127.0.0.1:8765 where each round delivers 10 short snippets with exactly one bug each, you type what the bug is, and hybrid scoring awards up to 100 points. Keys and config live under ~/Library/Application Support/Bugmiester/, the UI is static HTML, JavaScript, and Bootstrap, and an ops dashboard sits at /ops. Swift is the default language pack; JavaScript, Python, Rust, and C++ are also registered.

You launch with python -m bugmiester.

Three decisions

These are the craft bets I would defend in a design review, each one about honesty, ownership, or maintainability.

1. The trust boundary is the product.

Secrets stay in Application Support .env, the browser never sees keys, and the answer key is withheld on next-bug and revealed only on submit, or after recovery, while the server binds to localhost. That combination is the product, not a chat wrapper with a skin. I was counting on practice staying honest only if I cannot peek at the expected answer or grab a key from the page before I commit, and that binding to localhost with secrets in Application Support is enough trust for a machine I sit at. Pasting a key in the frontend or seeing expected text before I have typed mine is simply not available. The boundary is the reason the round is honest.

2. Scoring is built for fairness, not for the LLM.

Keywords run first (strong / weak / miss), and the LLM judge runs only on a miss. Give-up phrases score zero without a judge call. On a partial, a recovery quiz offers shuffled choices without leaking the expected summary while the quiz is open. A fixed offline eval suite and a documented acceptance checklist keep scoring changes honest. The hybrid path is there so I get a fair grade when my wording is close but not identical, without paying a judge call on every strong keyword hit, and without letting "I give up" farm a free model pass. I was counting on fair meaning close wording earns credit without matching the expected summary word for word, give-up phrases never buying a free model pass, and fairness showing up in a fixed offline suite rather than my mood that day. Keyword-first stays the happy path and the judge stays a backstop. The offline acceptance suite is how I stop myself from reshaping scoring on gut feel alone, because fairness has to be measurable or it is just a preference.

3. Curriculum is a system, not a prompt.

senior_mix ramps Simple → Common → Gnarly. Freshness uses scenario seeds, an avoid-list, similarity reject, and canned fallback when generation exhausts. Language packs keep the engine language-agnostic. Adaptation watches the isolation cluster (MainActor, sendable, concurrency): if Common-band misses pile up, Gnarly is delayed and Common is reinforced first, while strong players see no change. Difficulty and variety come from rules I can inspect, not from hoping the model keeps it interesting, so the ramp actually teaches, repeats do not feel identical, and the engine is not hard-wired to Swift. I was counting on a ramp teaching only when the rules are inspectable, on struggling with concurrency reinforcing Common before Gnarly rather than punishing, and on strong play staying uninterrupted by adaptation meant for someone else. Adaptation only intervenes when the isolation cluster says it should.

Proof

You can open a round on localhost and watch the score path yourself.

From the public repo and docs/ACCEPTANCE.md:

  • Mock full 10-bug round completes on localhost (round_possible=100, unique snippets)
  • No answer key on next-bug; no API key material in web/
  • Offline acceptance suite: 15 fixed eval cases, 30 good / 30 bad checks pass offline
  • Hybrid scoring, recovery quiz, freshness fallback, and ops analyze are covered by the acceptance checklist

Why I built it this way

These boundaries are the same ones I hold in iOS work: clear ownership, fair grading, and something a technical peer can judge quickly.

I keep keys and answers server-side so the browser cannot spoil the round. I use hybrid scoring so free text stays fair without making every grade a model call. I build a curriculum with rules so difficulty adapts instead of hoping a prompt does. AI-assisted writing is useful; it should not replace the ability to debug by reading.
